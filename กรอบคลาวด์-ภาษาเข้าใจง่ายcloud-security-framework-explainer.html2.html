Thailand’s National Cloud Security Framework · เวอร์ชัน 1.0 · ฉบับอ่านง่าย

กรอบการทำงานด้านการรักษาความมั่นคงปลอดภัยไซเบอร์ระบบคลาวด์

ประกาศสำนักงานคณะกรรมการการรักษาความมั่นคงปลอดภัยไซเบอร์แห่งชาติ วันที่ 10 มีนาคม 2568 โดย พลอากาศตรี อมร ชมเชย เลขาธิการ สกมช.

มีผลตั้งแต่วันประกาศ · ใช้เป็นแนวทางเตรียมความพร้อมก่อนมาตรฐานคลาวด์ พ.ศ. 2567 มีผลบังคับใช้ 10 กันยายน 2569

บทที่ 1 บทที่ 2 ต่างประเทศ บทที่ 3 เปรียบเทียบ บทที่ 4 ข้อเสนอ บทที่ 5 กรอบทำจริง คู่มือลงมือ

บทที่ 1 หนังสือเล่มนี้คืออะไร

เล่มนี้ไม่ใช่ตัวมาตรฐานบังคับ แต่เป็น กรอบทำงาน ที่ สกมช. ออกตามข้อ 7 ของมาตรฐานคลาวด์ พ.ศ. 2567 เพื่อให้หน่วยงานรู้ว่าต้องเตรียมอะไร ใครทำอะไร และเรียนจากประเทศอื่นอย่างไร

จำคู่กันสองฉบับ มาตรฐานคลาวด์ พ.ศ. 2567 = กติกาขั้นต่ำที่ต้องทำเมื่อมีผล 10 ก.ย. 2569
กรอบนี้ (มี.ค. 2568) = แผนเตรียมตัวและแนวทางขับเคลื่อนให้กติกานั้นเกิดจริง

ทำไมต้องมี

รัฐผลักดัน Cloud First ให้หน่วยงานย้ายงานขึ้นคลาวด์ แต่ภัยไซเบอร์ปี 2023 โดยเฉพาะการศึกษาและหน่วยงานรัฐเพิ่มขึ้น กรอบนี้เลยต้องการให้ทั้งลูกค้าคลาวด์ (CSC) และผู้ให้บริการ (CSP) พร้อมด้านคน กระบวนการ และเทคโนโลยี

วัตถุประสงค์การศึกษา 3 ข้อ

  1. เปรียบเทียบนโยบายและ National Cloud Security Framework ของต่างประเทศ
  2. เปรียบเทียบแนวทางและมาตรฐาน Cloud Security
  3. สนับสนุนการร่างกฎและมาตรฐานของไทย
ตัวอย่างสำหรับผู้ศึกษา ถ้าอาจารย์ให้รายงาน “ทำไมไทยไม่ลอก FedRAMP ทั้งดุ้น” คำตอบจากเล่มนี้คือ ไทยดูสิงคโปร์เรื่องแบ่งระดับ, สหรัฐเรื่องควบคุมละเอียด, ออสเตรเลียเรื่องคู่มือรัฐ, อินเดียเรื่องแนวทางภาครัฐ แล้วตัดให้เข้ากับ พ.ร.บ. ไซเบอร์ของไทย

บทที่ 2 ประเทศอื่นทำอย่างไร

กดแท็บดูทีละประเทศ เหลือแต่สาระที่ต้องจำ

หน่วยงานหลัก: IMDA กำหนดมาตรฐาน · CSA Singapore กำกับ MTCS

เครื่องมือ: MTCS SS / SS 584 แบ่งหลายระดับความปลอดภัย

ใครต้องทำ: CSP ที่ให้บริการในสิงคโปร์ต้องรับรองระดับที่เหมาะสม · ลูกค้าควรเลือกผู้ให้บริการที่ผ่าน MTCS

อ้างอิงมาตรฐาน: ISO 27001, 27017, CSA CCM, NIST 800-53

จุดเด่น: ยืดหยุ่นตามความสำคัญข้อมูล (เอกสารเล่มนี้พูดทั้งแบบ 3 ระดับและ 4 ระดับ ตามบริบท MTCS)

ตัวอย่างเทียบไทย ระดับต่ำ/กลาง/สูงของมาตรฐานไทย 2567 คล้ายแนวคิด “ข้อมูลยิ่งสำคัญ ต้องรับรองเข้มขึ้น” ของสิงคโปร์

หน่วยงานหลัก: NIST เขียนมาตรฐาน · FedRAMP รับรองคลาวด์สำหรับรัฐบาลกลาง

เครื่องมือ: NIST SP 800-53 (ชุดควบคุม), NIST SP 800-144 (แนวคลาวด์สาธารณะ)

ใครต้องทำ: หน่วยงานรัฐกลางต้องใช้คลาวด์ที่ผ่าน FedRAMP · เอกชนไม่ถูกบังคับแต่ยึดเป็นแนวทาง

จุดเด่น: ควบคุมละเอียดมาก (เอกสารระบุราว 20 ครอบครัวควบคุม / 265 รายการ) มี 3PAO ประเมิน

จุดอ่อนที่เล่มนี้เตือน: เอกสารยาว ซับซ้อน ค่าใช้จ่ายและเวลารับรองสูง

ตัวอย่าง กระทรวงในสหรัฐจะใช้ SaaS ใหม่ ต้องดูว่าบริการนั้นอยู่ในตลาด FedRAMP ไม่ใช่แค่ถูกและใช้ง่าย

หน่วยงานหลัก: ASD / ACSC จัดทำ Information Security Manual (ISM)

ใครต้องทำ: บังคับหน่วยงานรัฐบาลกลาง · เอกชนใช้เป็นแนวทาง

การจัดชั้นข้อมูล: Unclassified / Protected / Secret / Top Secret

จุดเด่น: รวม ISO 27000 กับแนว NIST แล้วปรับเป็นคู่มือรัฐ อัปเดตบ่อย

จุดอ่อน: บางส่วนเป็นข้อมูลความมั่นคง เผยแพร่ไม่หมด องค์กรเล็กทำตามยาก

ตัวอย่าง หน่วยงานภาษีออสเตรเลียใช้คลาวด์ได้ ถ้าผู้ให้บริการผ่านการประเมินสอดคล้อง ISM

หน่วยงานหลัก: MeitY · มี Cloud Security Guidelines / Baseline และระบบขึ้นทะเบียน CSP สำหรับงานรัฐ

ใครต้องทำ: ภาครัฐต้องเลือก CSP ที่ผ่านเกณฑ์ MeitY · เอกชนใช้เป็นแนวทาง

อ้างอิง: ISO 27001/27002, NIST 800-53/800-144, CSA CCM, แนว DevSecOps

จุดอ่อนที่เล่มนี้เตือน: ข้อกำหนดเข้ารหัสละเอียด คนเชี่ยวชาญขาด เอกสารอ้างอิงสาธารณะน้อย

ข้อดี–ข้อเสียมาตรฐานที่ประเทศเหล่านี้หยิบใช้ (สรุป)

มาตรฐานดีอย่างไรยากอย่างไร
ISO 27001/27017/27018โครงสร้างชัด ประเมินความเสี่ยงเป็นระบบ 27018 เน้นข้อมูลส่วนบุคคลบนคลาวด์ค่าใช้จ่ายรักษาใบรับรองสูง ต้องรวมหลายฉบับ
CSA STAR / CCMยืดหยุ่น หลายระดับ ทำมาเพื่อคลาวด์โดยตรงประเมินซับซ้อน CCM เป็นเมทริกซ์แนวทาง ไม่ใช่กฎหมาย
NIST 800-53 / 800-144ละเอียด เป็นที่ยอมรับกว้าง 800-144 เน้นคลาวด์สาธารณะยาว ปรับเข้าองค์กรยาก 800-144 ไม่ครอบคลุม private/hybrid ทั้งหมด
CIS Controlsทำได้เร็ว ประเมินเองได้ไม่ครอบคลุมทุกความต้องการองค์กร
ทดสอบความเข้าใจ

หน่วยงานรัฐไทยจะย้ายระบบทะเบียนที่มีข้อมูลส่วนบุคคลขึ้นคลาวด์สาธารณะ แนวคิดจากบทที่ 2 ที่ใกล้ที่สุดคือข้อใด




บทที่ 3 เปรียบเทียบกฎหมายและปัญหาจริง

3.1 กฎหมายที่มักพัน CSP

ประเทศกติกาหลักที่ CSP ชน
สิงคโปร์MTCS + PDPA + Cybersecurity Act + ETA + กติกาโทรคมนาคม/IMDA
สหรัฐฯNIST 800-53/800-144 ผูกกับ FISMA, Privacy Act, HIPAA (ข้อมูลสุขภาพ), FedRAMP, ยุทธศาสตร์คลาวด์รัฐ, OMB A-130
ออสเตรเลียISM + Privacy Act 1988 + Security of Critical Infrastructure Act 2018
อินเดียIT Act 2000, ระบบขึ้นทะเบียน CSP ของ MeitY, แนวสัญญาภาครัฐ, นโยบายไซเบอร์แห่งชาติ, ร่างกฎหมายข้อมูลส่วนบุคคล

3.2 กฎหมายที่มักพัน CSC (ลูกค้า)

ลูกค้าไม่ได้ปล่อยให้ CSP รับผิดแทนทั้งหมด ต้องมั่นใจว่าข้อมูลคน, ข้อมูลสุขภาพ, ข้อมูล CII และการโอนข้อมูลข้ามประเทศถูกกฎหมายของตัวเอง

ตัวอย่างไทย มหาวิทยาลัยรัฐใช้ Microsoft 365 เก็บข้อมูลนักศึกษา ต้องดูทั้งมาตรฐานคลาวด์ไทย, พ.ร.บ. คุ้มครองข้อมูลส่วนบุคคล และสัญญาว่าข้อมูลอยู่ประเทศใด — แนวเดียวกับสิงคโปร์ที่ PDPA ตามไปถึงข้อมูลที่เก็บนอกประเทศ

3.3 ตัวอย่างหน่วยงานที่ถูกกรอบเหล่านี้จับ

เล่มนี้ยกตัวอย่างกว้าง เช่น กระทรวงกลาโหม, หน่วยงานข่าวกรอง, สรรพากร, โรงพยาบาล, ธนาคาร, ผู้ให้บริการคลาวด์อย่าง AWS/Microsoft เพื่อชี้ว่า “งานรัฐ + งานอ่อนไหว” คือกลุ่มที่มาตรฐานเข้ม

3.4 ปัญหาซ้ำทุกประเทศ

  • ข้อกำหนดซับซ้อน หลายระดับ
  • ต้องปรับปรุงระบบต่อเนื่อง ไม่ใช่สอบผ่านครั้งเดียว
  • ตรวจประเมินและตรวจซ้ำมีค่าใช้จ่าย
  • คนเชี่ยวชาญไม่พอ โดยเฉพาะเรื่องเข้ารหัส
  • เทคโนโลยีเปลี่ยนเร็ว มาตรฐานตามไม่ทัน
ตัวอย่างปัญหาที่หน่วยงานไทยเจอได้ ซื้อคลาวด์แล้ว แต่ไม่มีคนทำ Self-assessment, สัญญาไม่ระบุเขตข้อมูล, แอดมินไม่มี MFA — นี่คืออุปสรรคแบบเดียวกับที่เล่มนี้สรุปจากต่างประเทศ ไม่ใช่แค่ “ยังไม่มีงบซื้อใบรับรอง”

3.5 กฎหมายข้ามประเทศ

ข้อมูลบนคลาวด์อาจถูกกฎหมายของประเทศผู้ให้บริการและประเทศเจ้าของข้อมูลพร้อมกัน

  • สิงคโปร์: PDPA ตามข้อมูลคนสิงคโปร์แม้เก็บนอกประเทศ · CSA มีอำนาจสั่งเข้าถึงระบบในสิงคโปร์
  • สหรัฐฯ: CLOUD Act ให้อำนาจเข้าถึงข้อมูลบนคลาวด์แม้เก็บนอกสหรัฐถ้ามีหมายศาล · มี HIPAA/CCPA/COPPA แยกเรื่อง
  • ออสเตรเลีย: APP 8 เรื่องโอนข้อมูลออกนอกประเทศต้องคุ้มครองพอ
  • อินเดีย: IT Act + ร่างกฎหมายข้อมูลส่วนบุคคล + กฎตัวกลาง
ตัวอย่างคำถามที่ต้องใส่ในสัญญา ถ้าศาลต่างประเทศขอข้อมูลหน่วยงานไทย ผู้ให้บริการจะแจ้งเราไหม ปฏิเสธได้แค่ไหน ข้อมูลสำรองอยู่ประเทศใด

บทที่ 4 สิ่งที่ไทยควรหยิบมาใช้

4.1 สิ่งที่ต่างประเทศทำแล้วไทยทำตามได้

  • มีหน่วยงานกำกับ CSP และ CSC ให้ชัด
  • บริหารความเสี่ยงทั้งสองฝ่าย และแบ่งตามระดับผลกระทบ/ความอ่อนไหว
  • มาตรการครบวงจร: บริหาร ระบุ ป้องกัน เฝ้าระวัง ตอบสนอง กู้คืน
  • รับรองตามระดับบริการ และตรวจซ้ำเป็นประจำ
  • มีขั้นตอนแจ้งเหตุที่ชัดและทันเวลา

4.2 ข้อเสนอเชิงนโยบายในเล่มนี้

กำกับดูแล

สกมช. กำกับ CSC ที่เป็นหน่วยงานตาม พ.ร.บ. ไซเบอร์ และ CSP ที่ขายงานให้หน่วยงานเหล่านั้น โดยตรงกับ CSP เอกชนอาจทำไม่ได้ จึงกำกับผ่านหน่วยงานรัฐ / ผู้ตรวจรับรองตามประกาศ พ.ศ. 2566

ความเสี่ยง

ใช้มาตรการในมาตรฐานคลาวด์ 2567 ทั้ง CSC และ CSP จัดระดับผลกระทบ และแยกข้อมูลอ่อนไหวโดยเฉพาะข้อมูลส่วนบุคคลตาม PDPA

มาตรการควบคุม

ให้ครบ Identify–Protect–Detect–Respond–Recover และเข้ากันได้กับ ISO 27001/27701/27017/27018, CSA STAR, NIST, FedRAMP

รับรองและเหตุการณ์

มีกลไก Self-assessment / Attestation / Certify Body คุณภาพระดับสากล และกลไกจัดการเหตุระดับประเทศ ภาคส่วน และหน่วยงาน

ตัวอย่างแปลงข้อเสนอเป็นงาน หน่วยงานไม่ต้องรอ สกมช. ครบทุกเครื่องมือก่อน เริ่มจัดระดับข้อมูล, เขียนตารางแบ่งหน้าที่กับ CSP, เปิด MFA, ตรวจที่ตั้งศูนย์ข้อมูลไทย ได้เลย

บทที่ 5 กรอบดำเนินงานของไทย — ส่วนที่ต้องทำตาม

5.1 วัตถุประสงค์กรอบนี้

  1. ผลักดันมาตรฐานคลาวด์ 2567 ให้เกิดเร็ว สะดวก มีประสิทธิภาพ
  2. ยกระดับความปลอดภัยทั้ง CSC และ CSP
  3. บูรณาการงานระหว่าง สกมช. กับหน่วยงานอื่น

5.2 ประโยชน์ที่เล่มนี้สัญญาไว้

  • ลดงานซ้ำ คนละมาตรฐาน คนละเช็คลิสต์
  • รัฐ–เอกชนร่วมกันทำคลาวด์ให้ปลอดภัยขึ้น
  • หน่วยงานย้ายขึ้นคลาวด์ได้เร็วขึ้น เพราะกติกาโปร่งใส

5.3 เอกสารที่ต้องวางคู่กัน

  • มาตรฐานคลาวด์ พ.ศ. 2567
  • มาตรฐานจัดคุณลักษณะข้อมูล/ระบบ พ.ศ. 2566
  • มาตรฐานผู้ให้บริการด้านไซเบอร์ พ.ศ. 2566
  • หลักเกณฑ์หน่วยงาน CII พ.ศ. 2564
  • หน้าที่ CII และหน่วยงานกำกับ พ.ศ. 2567
  • แนวทางจัดทำแผนรักษาความมั่นคงปลอดภัยไซเบอร์ พ.ศ. 2567

5.4 ใครคือใคร

1. กมช.

คณะกรรมการระดับชาติ ออกมาตรฐานขั้นต่ำตามมาตรา 9(4) พ.ร.บ. ไซเบอร์

2. คณะกรรมการเฉพาะด้าน Cloud First

ขับเคลื่อนนโยบายใช้คลาวด์เป็นหลัก จัดทำแนวจัดซื้อ ข้อมูล เลือกคลาวด์ ย้ายระบบ ติดตามผล

3. คณะกรรมการพัฒนารัฐบาลดิจิทัล

รายละเอียดการใช้คลาวด์ภาครัฐ จัดหา กำกับระบบนิเวศการจัดซื้อ

4. กกม.

กำกับ CII ตามมาตรา 53 ถ้าต่ำกว่ามาตรฐานและเพิกเฉย ส่งเรื่องให้สั่งแก้ไข

5. สกมช.

ประสาน ช่วยเหลือ เป็นศูนย์กลางความร่วมมือ เผยแพร่ความรู้ ฝึกอบรม ตามมาตรา 22

6–7. CSC และ CSP

CSC = หน่วยงานที่มีสัญญาใช้คลาวด์ · CSP = ผู้ทำให้บริการคลาวด์ใช้ได้และดูแลทรัพยากรให้พร้อม ปลอดภัย ขยายได้

8–10. ผู้ตรวจและผู้ปฏิบัติ

Certify Body ระดับก้าวหน้าขึ้นไป (ช่วงแรกใช้นานาชาติที่ สกมช. กำหนดได้) · Cloud Security Auditor ประเมินตามมาตรฐานหรือแนวสากล · Cloud Security Professional ปกป้องระบบคลาวด์และวางแผนรับมือภัย

ตัวอย่างบทบาท มหาวิทยาลัย = CSC · AWS/Azure/Google หรือคลาวด์ไทยที่ขายงานรัฐ = CSP · บริษัทตรวจ ISO ที่ สกมช. ยอมรับ = Certify Body · เจ้าหน้าที่รักษาความมั่นคงปลอดภัยสารสนเทศของมหาวิทยาลัย = Cloud Security Professional

5.5 ห้าขั้นทำงาน (ส่วนปฏิบัติหลักของเล่มนี้)

  1. กำหนดความต้องการร่วมกัน

    สกมช. สำรวจว่าทุกฝ่ายต้องการเครื่องมืออะไรเพื่อเอามาตรฐาน 2567 ไปใช้จริง เช่น

    • วิธีจัดระดับข้อมูล/ระบบ
    • วิธีแบ่งความรับผิดชอบ CSC–CSP
    • วิธี Self-assessment / Attestation / Certify Body
    • วิธี สกมช. รับรองตัว Certify Body และรายชื่อมาตรฐานสากลที่ยอมรับ
    • แนวปฏิบัติประกอบ, เทมเพลต, แพลตฟอร์มกลาง
    • กรอบบริหารความเสี่ยงคลาวด์, โมเดลสถาปัตยกรรม, White paper
    • พัฒนา Auditor และ Professional
    • ทีมเฉพาะกิจแก้ปัญหา
    ตัวอย่างที่หน่วยงานทำได้ทันที ส่งรายการระบบคลาวด์ที่ใช้อยู่ + ระดับข้อมูล + ช่องว่างในสัญญา กลับไป สกมช. เมื่อมีการเวียนขอความเห็น

  2. จัดลำดับความสำคัญ

    ของมีจำกัด เวลาก่อนบังคับใช้มีสองปี ต้องเลือกงานที่จำเป็นก่อน แล้วประกาศเจ้าภาพให้ทุกฝ่ายวางแผนและสื่อสารผู้บริหารชุดเดียวกัน

  3. จัดทำแผน (ตัวอย่างในเล่มเป็นแผน 5 ปี)

    ยุทธศาสตร์ตัวอย่าง 3 ก้อน

    • รวมพลังรัฐ–เอกชน: เครือข่ายอาสาสมัครผู้เชี่ยวชาญช่วยร่างหลักเกณฑ์ให้เร็วและเข้ากับหน่วยงานกำกับ
    • สร้างสภาพแวดล้อม: กลไกตรวจรับรอง, สกมช. รับรอง Certify Body, ลดอุปสรรค CSP ในและนอกประเทศ, ร่วมมือ CSA/ISO/NIST
    • พัฒนาคน: หลักสูตร Lead Auditor/Implementer, Cloud Security Professional, NCSA Cyber Clinic (SMART), health check, ช่องถามเรื่อง implement, Self-assessment

  4. ลงมือตามแผน

    มีทีมเฉพาะกิจอยู่ภายใต้เลขาธิการ สกมช. กำกับโดย กกม. และ กมช. และสอดคล้องทิศทาง Cloud First

  5. ประเมินผลต่อเนื่อง

    เวลาจำกัด ต้องวัดผลใกล้ชิด ปรับแผนได้ และเผยแพร่การเปลี่ยนผ่านแพลตฟอร์มกลางตามงบที่มี

ทดสอบความเข้าใจ

กรอบห้าขั้นนี้ใกล้กระบวนการใดที่สุด




คู่มือลงมือสำหรับผู้ที่จะทำตาม

รวมบทที่ 5 กับมาตรฐานคลาวด์ 2567 เป็นลำดับงานที่หน่วยงานทำได้เลย

  1. ทำบัญชีบริการคลาวด์สาธารณะทั้งหมด (SaaS, PaaS, IaaS, ไฮบริด)
  2. จัดระดับผลกระทบตามประกาศ พ.ศ. 2566 — ข้อมูลส่วนบุคคลอย่างน้อยระดับกลาง
  3. เขียนตารางแบ่งหน้าที่ CSC–CSP ตามประเภทบริการ
  4. ตรวจสัญญา: ที่ตั้งศูนย์ข้อมูลหลักในไทย, เขตอำนาจศาล, การแจ้งเหตุ, การลบข้อมูลเมื่อเลิกสัญญา, ผู้รับจ้างช่วง
  5. เปิด MFA บัญชีสิทธิสูง, ปิดบัญชีที่ไม่ใช้, เก็บ log
  6. วางการเข้ารหัสและกุญแจ — ถ้าใช้กุญแจของหน่วยงาน ห้ามให้ CSP ถือกุญแจนั้น
  7. เก็บหลักฐานเพื่อ Self-assessment หรือยื่นตรวจตามระดับ
  8. ซ้อมแจ้งเหตุร่วมกับ CSP ปีละครั้ง
  9. เมื่อดำเนินการเสร็จตามมาตรฐาน ส่งสรุปให้ สกมช. ภายใน 30 วัน
ข้อจำกัดของหน้านี้ เป็นคำอธิบายเพื่อการศึกษา ไม่ใช่สำเนากฎหมาย การตีความประกาศกรอบนี้เป็นอำนาจเลขาธิการ สกมช. และรายงาน กมช. คำวินิจฉัยของเลขาธิการเป็นที่สุด
